# Milgyo OS pre-open deep audit V85

Date: 2026-08-29
Baseline: V84 pre-open full replacement
Goal: code-level maximum confidence before public opening. This is not a literal 100% guarantee because Cloudflare Preview/Production, real D1/R2 bindings, network behavior, browser matrix, and production data cannot be fully reproduced in this isolated environment.

## Critical findings fixed

1. Fresh/recovery D1 migration chains were not self-contained.
   - Main DB migrations assumed runtime-created core tables.
   - Accounting DB migrations assumed `database/accounting-base-schema.sql` had been applied manually.
   - Added idempotent 0000 bootstrap migrations for both databases. Blank-DB sequential application now succeeds.

2. Electronic approval had a race window.
   - Simultaneous approval/rejection/recall could operate on the same document transition.
   - Added `document_transition_locks`, status-bound updates, current-line revalidation, deterministic approval audit IDs, and conflict responses.
   - Batch approval now binds updates to the expected status and refuses new-style approval-line documents to fall through to legacy fields.

3. Document create idempotency had a pre-check race.
   - `client_request_id` unique conflicts are now treated as an already-created request and return the existing document.

4. Accounting reconciliation target integrity existed mainly at application level.
   - Added DB triggers preventing two matched import transactions from pointing to the same accounting target.
   - Runtime schema verification checks trigger presence and pre-existing duplicates.

5. Password storage policy was too weak for a new deployment.
   - PBKDF2-SHA256 raised from 30,000 to 210,000 iterations.
   - Removed automatic fallback that could create new salted-SHA256 hashes.
   - Legacy/low-iteration hashes remain login-compatible and are upgraded after successful login.

6. Session rows could grow indefinitely.
   - Added periodic expiry cleanup and `expires_at` index.

7. Public health endpoint exposed more operational detail than needed.
   - Reduced to a generic readiness response; internal details remain server logs only.

8. Last-active-admin protection was vulnerable to concurrent mutations.
   - Update/delete SQL now includes the protection condition at mutation time, not only a prior COUNT check.

9. KST edge cases remained in a few year/date fallbacks.
   - Administrative numbering and UI default-date fallbacks now use Korea time where applicable.

10. V84 bulk accounting optimization still risked D1 invocation budgets on large jobs.
    - Transaction import now uses JSON1 set-based inserts with bounded payload chunks rather than one INSERT query per row.
    - 1,000-row imports remain supported without silent truncation.
    - Auto reconciliation candidate discovery is set-based (three ranked candidate queries), matched-target lookup is grouped, and result updates are set-based.
    - Donation export item creation and result application are set-based and guarded against duplicate concurrent result processing.
    - Receipt numbers can be reserved in a contiguous block rather than two sequence queries per receipt.

## D1 / Cloudflare operational rationale

Cloudflare's current D1 documentation states a per-Worker-invocation D1 query limit of 1,000 on Workers Paid and 50 on Workers Free. V84 had paths where hundreds of prepared statements could be executed for a large import or auto-match run. V85 reduces the principal large-job paths to a small number of set-based queries so these paths are materially safer even on the lower budget.

## Items that still require Preview/Production verification

The following cannot be proven in an isolated source audit:

1. Actual Cloudflare Pages production build with the exact lockfile dependencies.
   - `npm ci` was attempted but the package registry was unreachable/timed out in this environment, so a real Astro production build could not be completed here.
2. Real D1 migrations through Wrangler against Preview database state and migration bookkeeping.
3. R2 streaming behavior using the actual bindings and production-sized files.
4. Browser/manual flows: login, create document, multi-step approval, recall, send/receive, certificate issue/reprint, 1,000-row transaction import, 250-row auto-match, donation export/result application, tax ZIP export.
5. Production data-specific anomalies (for example, pre-existing duplicate reconciliation targets). V85 detects such duplicates and will refuse accounting readiness until they are corrected.

## Recommended deployment gate

1. Back up / Time Travel bookmark both production D1 databases.
2. Apply all pending MAIN DB migrations in Preview; confirm 0000/0007/0008 show as applied or already satisfied.
3. Apply all pending ACCOUNTING DB migrations in Preview; confirm 0000/0018 and prior 0017 are applied.
4. Deploy V85 to Preview.
5. Execute the manual smoke checklist above, especially two-browser simultaneous approval and large accounting jobs.
6. Run `database/accounting-production-checks.sql`; require zero critical counts and both reconciliation integrity triggers present.
7. Only then repeat migrations and deployment in Production.

## Confidence statement

Within the source code, migration, SQL, static security, TypeScript, and available regression-test scope, no known release-blocking defect remains after the V85 changes. Literal 100% correctness cannot be claimed until the same build, real bindings, real data, and browser flows pass in Cloudflare Preview.
