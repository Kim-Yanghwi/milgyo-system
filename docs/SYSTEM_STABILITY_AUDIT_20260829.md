# 종단관리시스템 화면·성능·안정성 점검 (2026-08-29)

이 문서는 2026-08-29에 제공된 `milgyo-system-main.zip`을 기준으로, 전자문서/대장/증명서 화면의 날짜 필터 정비와 함께 코드 전반의 저위험 성능·안정성 항목을 점검한 결과입니다.

## 1. 이번 버전에 실제 반영한 변경

### 날짜/검색 필터 레이아웃
- 전자문서(임시저장함~반려문서함 및 문서등록대장)의 시작일·종료일을 `filter-date-range` 한 그룹으로 묶었습니다.
- 두 날짜는 데스크톱에서 항상 한 줄로 유지하고, 기존 검색·정렬·조회·CSV 도구와 같은 툴바에 이어지도록 구성했습니다.
- 대장관리기능의 신청일 기간과 수계증서 발급대장의 수계일 기간도 동일한 컴팩트 그룹을 사용합니다.
- 공통 날짜 그룹의 날짜 한 칸 폭은 174px로 제한하여 기존처럼 컨테이너 전체 폭을 차지하지 않도록 했습니다.
- 전자문서 필터는 데스크톱에서 줄바꿈 대신 한 줄을 유지하며, 공간이 부족한 경우 툴바 내부 가로 스크롤을 사용합니다. 모바일(760px 이하)에서만 자연스럽게 줄바꿈합니다.

### 불필요한 대시보드 집계 제거
- 관리 하위화면(`ManagementLayout`)은 기존에 로그인 유효성 확인만을 위해 `/api/dashboard/summary`를 호출했습니다.
- 이 API는 여러 `COUNT`, 최근 문서 목록, 최근 접수·발송 목록까지 함께 조회하므로 세션 확인 용도로는 과했습니다.
- 신규 `/api/auth/session` 엔드포인트를 추가하고 하위화면에서는 이 경량 API만 호출하도록 변경했습니다.
- 전자문서 목록에서 필터/페이지를 바꿀 때마다 대시보드 집계를 다시 호출하던 흐름도 줄였습니다. 최초 진입 또는 실제 데이터 변경 후 강제 갱신이 필요한 경우에만 집계를 수행합니다.

### 조회 안정성/날짜 오류 보강
- 전자문서와 접수·발송 목록은 오래 걸린 이전 요청이 최신 결과를 덮어쓰지 않도록 요청 순번 검사를 적용했습니다.
- 전자문서·접수/발송·대장 조회 API에서 날짜 형식과 시작일/종료일 선후관계를 서버에서 검증합니다.
- 전자문서 `created_at`은 UTC ISO 시각이므로, 화면에서 선택한 날짜를 한국시간(KST) 00:00~24:00의 UTC 경계로 변환해 조회하도록 수정했습니다. 기존 구현은 `YYYY-MM-DDT00:00:00Z`를 사용하여 한국시간 00:00~09:00 문서가 다른 날짜로 조회될 수 있었습니다.
- 접수·발송 목록의 페이지 번호도 최대 10,000으로 제한하여 비정상적으로 큰 `OFFSET` 요청을 방지합니다.

### CSV 안전성
- 전자문서, 대장관리, 수계증서, 재직증명서 CSV 내보내기에서 셀 앞에 공백/탭/개행이 있더라도 `=`, `+`, `-`, `@`로 시작하는 값을 Excel 수식으로 실행하지 않도록 안전문자를 붙입니다.

## 2. 성능 점검 결과

### 현재 구조상 양호한 부분
- 메인 DB의 `ensureTables()`는 매 요청마다 전체 DDL을 반복하지 않고, 스키마 버전 확인 결과를 isolate 내에서 캐시/공유합니다.
- 문서, 결재선, 접수·발송, 대장, 수계증서에 주요 조회용 인덱스가 존재합니다.
- 홈 대시보드의 여러 수량과 최근 목록은 D1 `batch()`로 묶어 원격 DB 왕복을 줄이고 있습니다.
- 회계 업무는 5개 canonical domain으로 라우팅되고, 현재 UI가 legacy 회계 API를 직접 우회하지 않도록 회귀 테스트가 존재합니다.
- 회계 DB 스키마는 2026-08-21.1(v81)까지 순차 적용이 가능함을 SQLite에서 확인했습니다.

### 오픈 전 추가 최적화 완료 항목

#### A. 거래내역 가져오기 중복검사 N+1 — 개선 완료
`import-transactions`는 최대 1,000건의 외부키를 먼저 계산한 뒤 기존 키를 `IN (...)` 묶음 조회로 한 번에 확인하도록 변경했습니다. 입력파일 내부의 중복도 별도 Set으로 제거하며, 동시에 같은 파일이 들어오는 경쟁 상황에서는 `ON CONFLICT(external_key) DO NOTHING`으로 전체 배치 실패를 막습니다. 최종 가져오기 건수는 실제로 해당 batch에 저장된 행을 다시 집계해 기록합니다.

#### B. 자동대사 N+1 — 개선 완료
`auto-match`는 거래마다 후보를 찾고 후보마다 다시 대상/중복을 조회하던 구조를 제거했습니다. 배치/계좌 회계차원을 선조회하고, 후보 SQL 자체에서 상태·금액·방향·회계구분·회계조직·재원·카드 조건을 검증하며, 후보조회와 사용중 매칭키 조회를 D1 `batch()`로 묶습니다. 같은 실행 안에서 95점 이상 자동확정된 대상은 즉시 예약하여 뒤 거래가 같은 대상을 중복 확정하지 못하게 유지했습니다. 기존 `suggested` 상태였으나 재실행 시 유효 후보가 사라진 경우에는 `unmatched`로 정상 복원하도록 보강했습니다.

성능용 보조 인덱스는 `0017_v83_preopen_performance_indexes.sql`에 분리했습니다. 테이블/컬럼 계약 변경이 아니므로 `accounting_meta.schema_version`은 기존 `2026-08-21.1`을 유지합니다.

#### C. 첨부파일 다운로드의 Base64 변환 — 개선 완료
전자문서/접수·발송/대장 첨부파일의 현재 UI는 인증된 POST 요청에 `binary=true`를 보내고, R2 객체의 `body`를 그대로 응답 스트림으로 반환합니다. 따라서 R2 파일을 서버 메모리에 전부 올린 뒤 Base64로 약 33% 팽창시켜 JSON으로 보내는 경로를 정상 사용자 흐름에서 제거했습니다. D1에 남아 있는 구형 소용량 첨부와 외부 구형 호출을 위해 Base64 호환경로는 유지했습니다.

#### D. `%검색어%` 부분검색
문서/대장 검색 중 일부는 `LIKE '%검색어%'` 방식입니다. 앞쪽 와일드카드는 일반 B-tree 인덱스를 충분히 활용하기 어렵습니다. 현재 내부 업무량 규모에서는 문제가 작을 수 있지만 데이터가 크게 늘면 검색 전용 인덱스/FTS를 검토할 수 있습니다.

## 3. 코드 통합 상태 점검

ChatGPT 작성 부분과 이후 다른 도구에서 보완된 코드가 섞인 점을 감안해 다음을 확인했습니다.

- Git 충돌표시(`<<<<<<<`, `=======`, `>>>>>>>`) 잔존 없음
- 주요 소스의 `TODO/FIXME/HACK` 잔존 없음
- 공개 JavaScript 5개 파일 `node --check` 통과
- TypeScript `.ts` 94개 파일을 TypeScript transpile parser로 문법 검사 통과
- 관리화면 날짜/세션/범위검증/요청경합/CSV 관련 신규 회귀테스트 7개 통과
- 기존 회계 도메인 아키텍처 테스트 21개 통과(현재 실행환경에 `tsx`가 설치되지 않아 임시 Node type-stripping harness로 동일 테스트 소스를 실행)
- 회계 base schema + 회계 migration 13개(0004~0016) SQLite 순차 적용 성공
- 최종 `accounting_meta.schema_version`: `2026-08-21.1`
- 생성 테이블 61개 확인

## 4. 검증 제한

현재 샌드박스에서 npm 레지스트리 접근이 완료되지 않아 `npm ci`가 시간 초과되었고, 따라서 Astro 패키지를 포함한 정식 `npm run verify`/`astro build`는 실행할 수 없었습니다. 소스 문법·회귀테스트·SQL migration 검사는 별도로 수행했지만, 배포 전 GitHub/Cloudflare 빌드에서 최종 Astro 빌드 성공 여부를 확인해야 합니다.

## 5. 배포 후 권장 확인 순서

1. 전자문서 임시저장함/진행문서함/결재대기함/발송대기함/완료문서함/반려문서함/문서등록대장에서 날짜 2개가 한 줄인지 확인
2. 날짜 + 검색어 + 조회 + CSV가 데스크톱에서 같은 필터 줄에 있는지 확인
3. 대장관리기능과 수계증서 발급대장의 날짜 2개가 과도하게 길지 않은지 확인
4. 특정 하루의 00:00~09:00 KST에 생성된 전자문서가 해당 날짜 조회에 포함되는지 확인
5. 관리 하위페이지 이동 시 Network 탭에서 `/api/dashboard/summary`가 세션 확인 목적으로 반복되지 않고 `/api/auth/session`이 호출되는지 확인
6. Preview에서 500~1,000건 거래내역 가져오기와 100~250건 자동대사를 테스트 데이터로 실행해 응답시간과 결과건수를 확인
7. 전자문서/접수·발송/대장 R2 첨부파일 다운로드 시 Network 응답이 JSON/Base64가 아니라 바이너리 파일인지 확인
